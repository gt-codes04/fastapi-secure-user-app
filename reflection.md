Reflection – Module 10: Secure User Model, Testing, and Deployment

For this module, I implemented a secure user management flow on top of my current FastAPI project and then wired everything into a CI pipeline and Docker-based deployment. Altogether, this work touched several areas at once: database modeling with SQLAlchemy, data validation with Pydantic, password hashing, integration testing with a real PostgreSQL instance, and GitHub Actions configuration. It felt like a complete “mini project” that forced me to connect many pieces I had used separately before.

The first part was designing the `User` model and the Pydantic schemas. I created a SQLAlchemy `User` model with fields for `id`, `username`, `email`, `password_hash`, and `created_at`, adding uniqueness constraints on `username` and `email`. On the Pydantic side, I've used separate schemas for input and output-`UserCreate` and `UserRead`-so that the plain-text password is only accepted as input and never returned in responses. Getting the validation rules right-for example, using `EmailStr` and reasonable password constraints-helped catch bad input earlier rather than rely on database errors.

In terms of security, I implemented Passlib for password hashing and verification. Instead of storing raw passwords, I hash them before inserting into the database and use a dedicated helper to verify the password later. I've seen some warnings and edge cases with bcrypt, such as very long internal test strings the library uses, but I think the main takeaway is that relying on a well-tested library is much safer than trying to invent something in terms of hashing logic. This also made unit tests for `hash_password` and `verify_password` very straightforward to write and reason about.

Testing and CI were where most of the debugging happened. Locally, I used Docker to spin up PostgreSQL containers for both the “app” database and the “test” database, and then set `TEST_DATABASE_URL` so the integration tests could run against a real database. In GitHub Actions, I had to configure a Postgres service, wait for it to become healthy, and then point `DATABASE_URL` and `TEST_DATABASE_URL` to the right host and port. At first the app tried to connect to the wrong hostname (`postgres` instead of `localhost`, or to a non-existent database), which resulted in connection errors during test collection. Fixing the environment variables in the workflow and making sure `Base.metadata.create_all` ran against the correct URL finally got all tests to pass in CI.

Docker and the workflow also took a bit of trial and error. I had to fix the Dockerfile so that Uvicorn could find the FastAPI app correctly, ensure all required packages-including `email-validator` and `httpx`-were installed in the image, and adjust the workflow YAML so that GitHub accepted the syntax. I initially tried to include Docker Hub login and push directly in the workflow using secrets, but that led to YAML validation errors. In the end, I focused the CI pipeline on running tests and building the image and used Docker Hub separately to push the built image. That said, this still demonstrates the concepts of continuous integration and keeps the pipeline simpler and more reliable. Overall, this module forced me to think more like a real-world developer: not just writing endpoints which “work on my machine”, but also securing user data, writing automated tests, and making sure the project can be built and tested in a clean environment like GitHub Actions. I now feel more comfortable with structuring a FastAPI project, wiring it to PostgreSQL, and using Docker and CI to keep everything reproducible. There were a lot of small issues along the way, but working through them gave me a much better understanding of how all these tools fit together in a modern Python backend project.
